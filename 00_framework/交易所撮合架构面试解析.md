│      "exchange-trade-plate"     盘口变化                      │
└──────────────┬───────────────────────────────┬──────────────┘

│  ExchangeTradeConsumer        │  │  WebSocket(SimpMessaging)  │
│   - processExchangeTrade      │  │  Netty 长连接(APP)          │
│     (for update行锁+事务清算)   │  │  ExchangePushJob 300ms     │

**核心思想一句话**：撮合在内存（快、无锁、不管钱），清算在 DB（慢、有事务、管钱），中间用 Kafka 解耦（削峰、串行化、可重放）。这就是"CQRS / 读写分离"在交易系统的落地。

## 二、面试核心问题 1：无锁高并发方案怎么实现？

### 2.1 本项目的答案：单线程化 + 防御性细粒度锁

"无锁"的真正来源**不是** CAS/Disruptor 这些技术，而是**从架构上消除竞争**：

1. **每个交易对一个 CoinTrader 实例**（如 BTC/USDT 一个），订单簿是该实例的私有内存。
2. **Kafka 分区串行化**：一个分区同一时刻只被一个消费线程消费，且分区内消息严格有序。
   只要同一交易对的订单进同一分区，撮合就是天然单线程串行 —— 没有竞争，自然不需要锁。
3. **代码里的 `synchronized(list)` 是防御性的**：只锁单个方向的订单簿（如只锁买单簿），
   临界区全是纯内存 BigDecimal 运算（微秒级），用来防"撤单线程"（另一个 topic 的消费线程）
   与撮合线程并发改队列。即使竞争也几乎不阻塞。

### 2.2 业界常见方案对比（面试加分）

| 方案 | 代表 | 单交易对 TPS | 特点 |
|---|---|---|---|
| 数据库撮合 | 早期小交易所 | 几十~几百 | 订单簿落库，行锁+事务撮合，延迟高 |
| **内存撮合+细粒度锁（本项目）** | 中小交易所 | 数千~数万 | 单线程撮合，Kafka 串行化，异步清算 |
| LMAX Disruptor 无锁 RingBuffer | 币安早期、各大所核心 | 百万级 | 单线程消费环形缓冲，连 synchronized 都省掉；内存账本，DB 异步落库 |
| FPGA/硬件撮合 | 纳斯达克 | 千万级 | 硬件级并行，微秒以下延迟 |

### 2.3 本项目并发模型的三个隐患（主动讲体现深度）

1. **下单消息未指定 Kafka key**（`OrderController` 里 `send("exchange-order", json)`）：
   无 key 消息轮询/粘性分配分区，同一交易对订单可能散落多分区 → 多线程并发消费时**乱序**。
   正确做法：`send(topic, symbol, json)`，symbol 作 key 哈希到固定分区。
2. **tradingHalt/ready 是普通 boolean 非 volatile**：理论上有可见性问题，实际因 Kafka 消费
   线程模型风险极低，但严谨写法应加 volatile。
3. **TradePlate 用两把锁**（add/remove 锁 items，序列化推送锁 plate）：存在微小并发缝隙，
   更严谨应统一为同一把锁。

## 三、面试核心问题 2：盘口（订单簿）怎么实现？

### 3.1 数据结构（CoinTrader 中）

```java
// 买单簿：价格降序 → firstKey 就是"买一"
TreeMap<BigDecimal, MergeOrder> buyLimitPriceQueue  = new TreeMap<>(Comparator.reverseOrder());
// 卖单簿：价格升序 → firstKey 就是"卖一"
TreeMap<BigDecimal, MergeOrder> sellLimitPriceQueue = new TreeMap<>(Comparator.naturalOrder());
// MergeOrder = 同一价格档位的订单列表(ArrayList)，按到达顺序排 → 时间优先(FIFO)
// 市价单队列：LinkedList，只排时间
LinkedList<ExchangeOrder> buyMarketQueue / sellMarketQueue;
// 盘口（前端展示用，与订单簿冗余存储、同步维护）
TradePlate buyTradePlate / sellTradePlate;  // 各100档
```

**两层结构是标准做法**：`价格档位(Level) → 档内订单队列(Queue)`。
因为一个价格可挂多笔订单，TreeMap key 唯一，所以 value 必须是列表。

### 3.2 为什么用 TreeMap 不用 PriorityQueue？

- 撤单要"按价格定位档位"：TreeMap.get(price) = O(logN)；堆删任意元素 = O(N)。
- 撮合从最优价开始逐档扫：TreeMap 迭代器天然有序。
- 缺点：红黑树指针跳转多、CPU 缓存不友好。顶级引擎用"价格离散化+数组+位图"或跳表。

### 3.3 TradePlate（盘口展示）的设计

- **冗余存储、同步维护**：挂单时 add() 累加档位量，成交/撤单时 remove() 扣减，扣到 0 删档。
- 好处：推送时直接序列化，不用遍历订单簿临时聚合（**用内存换 CPU**）。
- 只保留前 100 档（maxDepth），超出深度的挂单仍参与撮合，只是不展示。
- 推送是**全量推 100 档**，高频时网络开销大；业界做法是推增量 diff（如币安 depth stream）。

## 四、面试核心问题 3：撮合算法流程

入口 `CoinTrader.trade(order)`：

```
新订单(taker)进来
 ├─ 市价单 → 只与对手方【限价簿】撮合（市价单之间无法定价，不直接撮合）
 │           剩余 → 挂本方市价队列等待（注意：主流交易所是 IOC 直接撤销，本项目会滞留）
 └─ 限价单 → ① 先与对手方【限价簿】撮合（matchLimitPriceWithLPList）
             ② 剩余再与对手方【市价队列】撮合（matchLimitPriceWithMPList）
             ③ 仍剩余 → 挂入本方限价簿，taker 变 maker
```

**撮合循环（价格优先+时间优先）**：

```
外层：从对手簿最优价档位开始遍历（TreeMap 有序 = 价格优先）
  ├─ 买单：对手价 > 我的买价 → break（后面更贵，不必再看）
  └─ 卖单：对手价 < 我的卖价 → break
内层：同档位内按到达顺序逐单撮合（ArrayList = 时间优先/FIFO）
  ├─ 成交量 = min(双方剩余量)         ← 部分成交是常态
  ├─ 成交价 = maker(挂单方)的价格     ← 保护 taker，国际惯例
  ├─ maker 完全成交 → 从档位移除
  └─ taker 完全成交 → 结束
档位被吃空 → 从订单簿删除该价格档
```

**关键细节**：
- 市价买单的 `amount` 存的是**成交额(USDT)**不是币数量，剩余可成交量 = 剩余成交额/成交价（ROUND_DOWN 向下取整，宁可少买不多扣）。
- `adjustMarketOrderTurnover`：市价买单最后剩"买不起最小精度"的零头时，并入最后一笔成交让订单完结（**尾差处理**，金额系统通用套路）。
- 撮合全程**只改内存对象的 tradedAmount/turnover，零 DB 操作**；完成后才发 Kafka 异步落库。
- 发 Kafka 在 `synchronized` **锁外**进行 —— IO 不占撮合锁，关键性能细节。
- 成交/完成消息按 1000 条/批拆分发送，防单条消息超 Kafka 1MB 上限。

## 五、面试核心问题 4：Kafka 如何保证消息顺序与幂等？

### 5.1 顺序性

| 环节 | 机制 | 本项目情况 |
|---|---|---|
| Broker | 分区内严格有序（offset 递增） | ✅ 天然支持 |
| 生产者 | 同一 key → 同一分区 | ⚠️ **未指定 key**（隐患，见 2.3） |
| 生产者 | 重试不乱序：`enable.idempotence=true` 或 `max.in.flight=1` | ⚠️ 未配置（retries=3 时可能乱序） |
| 消费者 | 一个分区只被一个线程消费 | ✅ concurrency=9，需分区数≥9 |
| 消费者 | 批量处理同分区消息时串行执行 | ✅ for 循环逐条 trade() |

### 5.2 不丢消息

- 生产端：`acks=all`（等全部 ISR 副本确认）—— ⚠️ 本项目未设置，默认 acks=1 有丢消息风险。
- 消费端：`enable.auto.commit=false` + Spring 容器 BATCH 提交（处理完一批才提交 offset）
  = **at-least-once**：宕机重复消费，但不丢。✅ 本项目如此。

### 5.3 幂等（重复消费怎么办）—— 本项目三级幂等

1. **状态机幂等（最有效）**：订单 `TRADING → COMPLETED/CANCELED` 终态不可逆。
   `tradeCompleted`/`cancelOrder` 先校验 `status==TRADING`，重复消息直接拒绝。✅
2. **乐观锁 SQL 幂等**：`thawBalance` 带 `frozenBalance >= amount` 条件，重复执行影响 0 行。✅
3. **缺口**：`processExchangeTrade`（成交清算加币扣币）**无防重**！
   重复消费会重复清算。面试标准答案：成交记录建唯一索引/去重表，或 Redis SETNX(tradeId)。

### 5.4 Kafka 在本架构中的真正价值（超越"消息队列"的理解）

- **串行化器**：把并发下单请求排队成分区内串行流 → 撮合无锁的前提。
- **削峰填谷**：下单洪峰积压在 topic，撮合按自己节奏消费。
- **WAL/事件溯源**：撮合结果先发 Kafka 再异步落库，宕机后可重放恢复。
- **解耦**：撮合引擎（有状态、单点）与 API/清算（无状态、可扩展）独立部署。

## 六、面试核心问题 5：无锁无事务下如何保证资金安全？

资金安全**不在撮合引擎**（它只算"谁和谁成交多少"，不碰钱），而在前后两道 DB 防线：

### 6.1 第一道：下单冻结（addOrder，@Transactional）

```sql
-- 乐观锁/CAS 思想：检查+扣减一条原子 SQL 完成，杜绝"先查后扣"的 TOCTOU 超卖
update member_wallet set balance = balance - :x, frozenBalance = frozenBalance + :x
 where id = :id and balance >= :x   -- 余额不足 → 影响0行 → 拒单
```
- 限价买单冻结 `价格×数量`（按最坏情况冻）；市价买单冻结全部成交额；卖单冻结数量。
- **先冻结再撮合** → 撮合时无需查余额 → 内存撮合零 DB 的前提。

### 6.2 第二道：成交清算（processExchangeTrade，@Transactional）

```sql
-- 固定顺序加锁防死锁：永远先锁买方 memberId 的钱包行，再锁卖方
select id from member_wallet where member_id = ? for update;
```
- **防死锁 = 固定加锁顺序**（经典面试题"两个账户转账如何加锁"的标准答案之一；
  更通用写法是按 memberId 大小排序加锁）。
- 事务内：买方 +币(扣手续费) -冻结的USDT；卖方 +USDT(扣手续费) -冻结的BTC；
  加成交明细、资金流水、推广返佣。任一失败整体回滚。

### 6.3 第三道：完成/取消退款（tradeCompleted/cancelOrder + orderRefund）

- 退款 = 冻结的 − 实际消耗的（限价买单按更优价成交的差额退回，用户不吃亏）。
- 状态机校验保证"一笔订单要么算成交要么算取消，不会既成交又退款"。

### 6.4 已知风险点（面试主动讲）

1. **下单"DB 提交"与"发 Kafka"非原子**：事务提交后、发 Kafka 前宕机 → 订单在 DB 是
   TRADING 但撮合器收不到 → 资金永久冻结。业界解法：本地消息表 / RocketMQ 事务消息 / Outbox 模式。
2. **清算无幂等防重**（见 5.3）。
3. **清算线程池 AbortPolicy**：队列(1024)满时任务被拒直接丢失，靠 offset 未提交重放兜底。
4. **清算异常被 catch 吞掉**：只 printStackTrace，无死信队列/告警。

## 七、单节点并发边界估算

### 7.1 各环节理论能力

| 环节 | 瓶颈 | 估算 |
|---|---|---|
| 下单 API | MySQL：冻结+插单 2 次写/单，行锁竞争 | **1,000~3,000 单/秒**（全系统总入口瓶颈） |
| Kafka 传输 | 单分区单线程消费 | 数万~10万+ 条/秒（不是瓶颈） |
| **内存撮合（单交易对）** | 单线程 CPU：TreeMap O(logN) + BigDecimal | **5,000~20,000 笔/秒**（盘口浅、日志少时更高；本项目 log 较多会打折） |
| 清算回写 | MySQL：每笔成交 ~10 次 SQL + for update 行锁 | **300~1,000 笔/秒**（同一用户并发清算会排队） |
| 行情推送 | 300ms 批量合并 + WebSocket/Netty | 数千连接/节点（Netty 可上万） |

### 7.2 结论

- **撮合本身不是瓶颈**（内存单线程每秒数千~数万笔足够），**瓶颈在两头的 MySQL**：
  入口的下单冻结、出口的成交清算。
- 单节点（单撮合实例）实际可用量级：**全站下单 1k~3k TPS、单交易对撮合 5k~20k TPS、
  成交清算 300~1k TPS**。日成交笔数千万级以内可以支撑。
- 要再往上走：账户余额内存化（内存账本+Disruptor）、清算批量化、DB 分库分表。

## 八、部署方案（你的理解是对的）

- **不支持高可用**：撮合状态全在内存，没有主备/集群。单点宕机 → 该节点上所有交易对停撮合，
  重启后靠 `CoinTraderEvent` 从 DB 捞 TRADING 订单 + 成交明细重算已成交量，重建订单簿
  （恢复期间 ready=false，新订单直接撤单退款）。
- **按交易对拆分部署（水平分片）**：
  - 热门交易对（BTC/USDT、ETH/USDT）**独占一个节点**，吃满单机性能；
  - 冷门交易对**多个合并部署**到一个节点（一个进程可持有多个 CoinTrader，
    `CoinTraderFactory` 就是个 Map）。
  - 拆分落地方式：不同节点加载不同交易对集合（需配合配置隔离，本项目默认单节点全量加载）。
- 同一交易对**永远无法横向扩展**（单线程撮合的本质限制），只能升配单机 CPU
  （单核性能优先，因为撮合是单线程）或换 Disruptor/FPGA 方案。

## 九、面试问答速查表

**Q: 你们的撮合引擎为什么快？**
A: ① 订单簿全内存（TreeMap+ArrayList），撮合路径零 DB；② Kafka 分区串行化实现单线程撮合，
无锁竞争；③ 资金在下单时已冻结，撮合不管钱；④ 结果异步发 Kafka，清算/推送全异步。

**Q: 盘口用什么数据结构？**
A: 买单 TreeMap 降序、卖单 TreeMap 升序，value 是同价订单的 FIFO 队列（MergeOrder）。
选 TreeMap 是因为撤单要 O(logN) 按价定位，堆做不到。展示盘口冗余一份 TradePlate 同步维护，
用内存换 CPU。

**Q: 撮合规则？**
A: 价格优先、时间优先；成交价取 maker 价；限价单先吃限价簿再吃市价队列，剩余挂簿；
市价单只吃限价簿，剩余滞留市价队列（可聊 IOC 改进）。

**Q: Kafka 怎么保证顺序和幂等？**
A: 顺序靠"key 哈希定分区 + 分区内有序 + 单线程消费"（并指出本项目没传 key 的改进点）；
不丢靠 acks=all + 手动提交 offset（at-least-once）；幂等靠消费端状态机（TRADING 校验）
+ 乐观锁 SQL，并主动说 processExchangeTrade 的防重缺口及唯一键/SETNX 解法。

**Q: 无锁无事务怎么保证资金安全？**
A: 撮合引擎不碰钱。资金三段式：下单乐观锁冻结（balance>=x 条件更新防超卖）→
清算 for update 固定顺序行锁防死锁 + 事务 → 完成/取消状态机幂等退款。
再补一刀：DB 提交与发 Kafka 非原子的风险及本地消息表解法。

**Q: 怎么做高可用？**
A: 本项目不支持。业界方案：① 主备撮合 + 状态同步（输入流重放到备机，如 LMAX 的
replication）；② 内存快照 + WAL 快速恢复；③ 按交易对分片 + 故障转移（备机接管分区）。
本项目只有"DB 重建订单簿"的冷恢复。

**Q: 单节点能撑多少并发？**
A: 见第七节：入口下单 1k~3k TPS（DB 瓶颈），单交易对撮合 5k~20k TPS（单线程 CPU），
清算 300~1k TPS（DB 瓶颈）。优化方向：内存账本、批量清算、Disruptor。
