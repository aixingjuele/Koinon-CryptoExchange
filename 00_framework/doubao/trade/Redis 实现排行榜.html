Redis 实现排行榜（面试版，钱包后端常用，高频题）

核心方案：Sorted Set（ZSet 有序集合）

底层：跳表 + 哈希表。 ZSet 结构：key: member(成员)，score(分数)

  • 同一个 key 下，​member 唯一​，score 可以重复；
  • 按 score 从小到大排序；取数据可以倒序（从高到低，排行榜常用）。

场景举例：用户资产排行榜、交易金额排行、积分排行。 贴合你的钱包业务：用户账户总资产排名。

基础命令

# 添加/更新分数，用户id=u001，资产 1200
ZADD rank:asset 1200 u001

# 查询前1名，从高到低 WITHSCORES 带出分数
ZREVRANGE rank:asset 0 10 WITHSCORES

# 获取某个用户当前排名（从第0开始）
ZREVRANK rank:asset u001

# 获取用户分数
ZSCORE rank:asset u001

# 删除用户
ZREM rank:asset u001
​

业务逻辑（钱包资产榜举例）

  1. 用户资产变动时（充值 / 提现 / 交易），​计算最新总资产​，执行 ZADD
    • ZADD 存在则​覆盖 score​，不存在新增，一行命令搞定更新。
  2. 查排行榜：ZREVRANGE 拿 TOP N。
  3. 查个人在全榜排第几：ZREVRANK。

关键问题 & 面试必问坑点

1. 分数相同怎么办？

ZSet 规则：score 相同，​按 member 字典序排序​。 业务缺陷：资产一样的两个人，排名会固定按 id 排序，不是并列。 ✅ 解决办法： 把 score 设计成 资产 + 微小时间偏移例如：score = 总资产 * 100000000 + (99999999 - timestamp)资产优先；资产相同，​晚更新的人排名靠后​，实现近似并列效果； 读取的时候再把分数还原。

2. 大数据量性能？

ZSet 查询 TOP N 复杂度 O (logN + K)，K 是取出条数，​拿 TOP100 非常快​。

不适合：一次性导出全量百万用户榜单（开销大）。

3. 持久化与一致性问题（后端重点）

Redis 是缓存，​不能作为唯一数据源​。

  • 资产的真实数据一定存在数据库（MySQL）；Redis 排行榜只是​缓存视图​。
  • 两种更新策略：
    1. 实时更新：用户资产变更，DB 写完后，同步更新 ZSet（简单，高并发有不一致风险）
    2. 定时全量刷新：定时任务（比如每 5 分钟）从 DB 批量拉取全部用户资产，重建 ZSet，适合允许榜单短暂延迟的场景。

4. 分页怎么实现？

ZREVRANGE rank:asset start end例：第 1 页 TOP10：0~9；第 2 页：10~19。 ⚠️ 缺陷：​有数据插入 / 删除时，分页会出现重复、漏行​（和数据库 offset 分页类似），排行榜业务一般可接受。

备选方案对比（面试官很爱问）

  1. ZSet（推荐）：实时性好，简单，适合 TOP 榜单，绝大多数排行榜首选
  2. MySQL order by + limit：数据量大时，order by 全表排序，性能差，不适合高频查询排行榜
  3. Redis Hash：只能存 K-V，不能排序，不能直接做排行榜

并发风险

多线程同时更新同一个用户分数：ZADD 是​单命令原子操作​，不用自己加锁，不会出现并发覆盖问题。

扩展：如果需要多榜单

比如：总资产榜、24h 交易量榜。 直接分开 key：rank:total_asset、rank:volume_24h

面试口述精简版（1 分钟）

做排行榜优先使用 Redis ZSet 有序集合。member 是用户唯一标识，score 作为排行依据。 ZREVRANGE 倒序取 TOPN，ZREVRANK 查个人名次。ZADD 原子更新分数。 注意两点：score 相同会按 member 字典序排序，需要做分数改造模拟并列；Redis 榜单是缓存视图，真实数据落数据库，根据业务选择实时更新或者定时刷新榜单。ZSet 取 TOPN 性能很好，但全量遍历成本高。
