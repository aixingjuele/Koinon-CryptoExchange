Redis 热 key 问题 面试版（后端高频，钱包业务场景适用）

热 key：某个 key 被超高 QPS 访问，所有请求打到同一个 Redis 实例，造成单节点 CPU / 网卡打满，集群分片失衡。 例子：全网资产排行榜 key、全局配置、公共代币基础信息、活动总开关，都容易变成热 key。

一、先确认：怎么发现热 key

  1. 客户端埋点，统计 key 访问次数
  2. Redis 自带 redis-cli --hotkeys（Redis4.0+）
  3. 监控平台：看各实例 CPU、入流量，某实例负载远高于其他分片，大概率存在热 key

二、解决方案（按优先级排序，面试按这个顺序讲）

方案 1：本地缓存（最优先，最简单有效）

在应用服务器内存里做一层本地缓存（Caffeine / Guava Cache）。

  • 逻辑：请求先读本地缓存，过期时间设置短一点（比如 1~5s）；本地失效，再去查 Redis。
  • 优点：直接挡住绝大部分请求，不会打到 Redis 集群。
  • 缺点：多实例本地缓存数据会短暂不一致；适合允许短时间数据不一致场景（排行榜、基础配置）

钱包场景：代币基础信息、排行榜 TOP 列表，非常适合。

方案 2：热 key 分片（key 拆分，Redis 集群层面解决）

把​同一个逻辑 key 拆成 N 个物理 key​，请求随机路由到其中一个分片。 举例： 原 key：rank:asset拆成：rank:asset_0、rank:asset_1 ... rank:asset_9写：更新全部 10 个分片 读：随机选其中一个读取

读请求被分散到多个 Redis 节点，把压力打散。

  • 优点：不依赖应用内存，数据一致性比本地缓存好一点
  • 缺点：写放大，一次更新要写 N 份；数据多副本，占用更多内存。 适合：读远大于写的场景（排行榜）

方案 3：Redis 集群代理层做热 key 缓存（中间件方案）

比如使用 Redis Proxy（Tair Proxy / Codis Proxy），代理层内置热 key 缓存。 代理识别热 key，在代理层缓存返回，请求不穿透到后端 Redis 节点。 适合大厂，改造成本高。

方案 4：业务层改造，避免热点

  • 把大 key 拆小；不要把大量数据塞到单个 key
  • 合并请求，批量查询，减少 QPS
  • 降级：高峰期直接返回兜底静态数据

方案 5：临时兜底熔断

当监控探测到该节点负载过高，直接熔断，返回缓存兜底数据，保护 Redis 节点。

三、面试高频坑点 & 追问

  1. 本地缓存过期雪崩问题不要统一过期，给过期时间加随机偏移量（抖动 jitter），防止同一时刻大量缓存失效，请求瞬间击穿 Redis。
  2. **热 key 分片，写放大怎么处理？**写请求本身不多的场景适合；如果写 QPS 也很高，这个方案会放大写压力，就不推荐。
  3. 热 key vs 大 key 区分（面试官很容易顺带问）
  • ​热 key​：访问 QPS 极高（请求多），value 不一定大
  • ​大 key​：value 体积很大，读取耗时，不一定访问频繁

1 分钟口述精简版

热 key 是单个 key 请求集中打到同一个 Redis 分片，造成单节点负载高。 优先方案是​应用本地缓存​，Caffeine 这类，设置较短过期时间加随机抖动，拦截大部分请求，适合允许短暂不一致场景。 第二个方案是​key 分片​，逻辑 key 拆成多个物理副本，读请求随机访问分片打散压力，但会带来写放大。 还可以用代理层的热 key 缓存；极端情况做业务降级熔断。同时要区分热 key 和大 key，二者优化手段不一样。
