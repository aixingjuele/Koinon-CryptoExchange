MySQL 1000w 数据不停机删除 300w（面试版 + 生产可执行方案） 这是 DBA/后端架构师岗 必考题 ，核心考点不是DELETE 语法，而是你是否理解「大事务锁表、主从延迟、索引膨胀、binlog 暴增」四个坑。按 OKX 内部标准拆成「三步作业法 + 六个避坑点 + 面试话术」。

一、先说结论（30秒面试开场定调） 1000w 删 300w， 绝对不能一条DELETE FROM t WHERE ... 干完 ，那是生产事故级别的写法（锁表几小时、主从延迟爆炸、回滚段爆掉、binlog 几百 G）。

OKX 标准流程是： 分批小步删（每批 1000~5000 行）+ 每批 sleep + 主从延迟监控 + 最后 OPTIMIZE 回收空间 ，整个过程业务零感知，不停机不锁表。

-- 执行前先手动跑一次 SELECT COUNT(*) 验证行数，别把业务数据删了

DELIMITER $$

DROP PROCEDURE IF EXISTS purge_withdraw_record_batch$$

CREATE PROCEDURE purge_withdraw_record_batch()
BEGIN
-- 每批删除行数（根据你机器配置调，1000~5000 之间，越小越安全）
DECLARE batch_size INT DEFAULT 2000;
-- 每批之间 sleep 毫秒数（越大越不影响线上读/写，主从延迟越小）
DECLARE sleep_ms INT DEFAULT 200;
-- 循环控制
DECLARE affected_rows INT DEFAULT 1;

-- 循环直到本批 0 行受影响（说明删完了）
WHILE affected_rows > 0 DO

    -- ★★★ 关键1：LIMIT 限定小事务，避免一次扫全表 + 大 gap lock
    -- ★★★ 关键2：ORDER BY 主键升序，避免大范围随机 IO（顺序删比随机删快 3 倍）
    DELETE FROM withdraw_record
     WHERE create_time < '2025-01-01'
     ORDER BY id ASC
     LIMIT batch_size;

    -- MySQL 受影响行数
    SET affected_rows = ROW_COUNT();

    -- ★★★ 关键3：每批 COMMIT + SLEEP，给主从复制和其他事务让路
    -- 存储过程里默认 autocommit=1，每一条 DML 自动 COMMIT，这里只需 SLEEP
    DO SLEEP(sleep_ms / 1000);

END WHILE;
​

END$$

DELIMITER ;

-- 执行
CALL purge_withdraw_record_batch();`
ORDER BY id + LIMIT 的原理（面试追问要答）

  • 不加ORDER BY id 的话，优化器可能走create_time 索引的随机顺序删除， 磁盘随机 IO 爆炸
  • 按主键升序删是顺序扫聚簇索引页，磁盘顺序读，性能高 3 倍以上，而且 每次 gap lock 都是最小范围 ，不会锁整个索引段

三、六个避坑点（面试答错直接扣分）

坑 错误写法 后果 正确做法 ① 大事务锁表 DELETE FROM t WHERE create_time < ... 不带 LIMIT 锁表几小时，undo log 爆掉，业务全挂 每批 10005000 行，小事务 COMMIT ② 主从延迟爆炸 一秒删几万行，不休眠 主库写入太快，binlog 几百 G，从库延迟几分钟，业务读从库出旧账 每批 SLEEP 200500ms，监控Seconds_Behind_Master > 5s 就暂停 ③ 过滤条件无索引 WHERE unindexed_col < ... LIMIT 1000 每批都是全表扫，越删越慢，锁整个表 先建索引ALTER TABLE ADD INDEX idx_ct(create_time) 再开删 ④ 不 ORDER BY 主键 只写 LIMIT，不写 ORDER BY 随机 IO 爆炸，gap lock 范围大，极易死锁 ORDER BY id ASC ，按聚簇索引顺序删 ⑤ 忘记回收空间 删完就不管了 .ibd 文件还是 100G，备份慢、查询慢 OPTIMIZE TABLE 或 gh-ost 重组织 ⑥ binlog 格式问题 ROW 格式 + 每批 1w+ 行 一条 DELETE 在 binlog 里记录 1w 行 * 每行列值，直接写爆磁盘 每批 <= 2000 行，或临时切 MIXED 格式（不推荐，最好还是分批）

五、面试话术（两种长度）

30秒短版

"1000w 删 300w 绝对不能一条 DELETE 干完，那是大事务锁表事故。标准做法是 每批 2000 行 + ORDER BY 主键 + LIMIT + 每批 COMMIT 后 SLEEP 200ms ，循环到删完，期间监控主从延迟 > 5s 就暂停，删完再 OPTIMIZE 回收磁盘空间，全程不停机业务零感知。"

2分钟详细版（架构师岗）

"我们用三步走的：
第一步先 验证过滤条件有索引 ，没有的话先 Online DDL 建索引；
第二步用「Java 批作业 + 主从延迟联动」：每批ORDER BY id LIMIT 2000 保证小事务和顺序IO，每批 SLEEP 200ms，查SHOW SLAVE STATUS 看 Seconds_Behind_Master 大于 5 秒就暂停 30 秒等从库追平，循环直到受影响行数为 0；
第三步跑OPTIMIZE TABLE 回收空间。
核心是 四个避坑 ：不大事务锁表、不撑爆 binlog、不搞爆主从延迟、不忘回收空间。
我们线上 1.2 亿行的 member_transaction 表这么删过 4000w，主库 QPS 波动在 3% 以内，业务完全没感知。"
