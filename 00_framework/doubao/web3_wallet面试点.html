一、钱包账户体系（JD 重点·异构融合与抽象）

✅ 面试必背：6 种账户形态的安全模型与使用场景

💡 ​迁移 CoinExchange 经验​：面试官问"异构账户怎么融合抽象"——答：就像我们在 CoinExchange 里对不同 ExchangeOrderType（限价/市价）抽象出统一 processOrder() 清算流程一样，钱包侧做两层抽象：

  1. ​SPI 抽象层​：SignerProvider 接口，定义 signTransaction(payload, accountId)，每种账户一个实现（HdSigner/MpcSigner/TurnkeySigner）
  2. ​统一账户模型​：Account 表统一主键 web3_id，字段区分 account_type + provider_config_json，上层业务完全感知不到差异

✅ HD 钱包派生路径速记（面试被问 BIP 系列直接答）

   ↓ PBKDF2-HMAC-SHA512

   m / 44' / coin' / account' / change / index
       │     │      │          │       │
       │     │      │          │       └─ 0=外部收款 1=找零地址
       │     │      │          └─ 固定 0/1
       │     │      └─ 用户账户索引（从 0' 开始）
       │     └─ SLIP-44 币种号（0'=BTC, 60'=ETH, 501'=SOL）
       └─ BIP-44 固定目的码（硬化派生 '）

​硬化派生 vs 非硬化的坑​（面试 90% 会问）：

  • ​硬化 i'（i+0x80000000）​：必须拿父私钥才能推导 → 安全，​账户级必须硬化​（避免公钥派生泄露账户）
  • ​非硬化 i​：拿父公钥 + 子索引就可以推导 → 适合收款地址 index 批量生成（BIP-44 最后两级用非硬化）

二、钱包核心服务（资产·交易历史·亿级存储）

✅ 四大核心链路的幂等 + 一致性方案（迁移 CoinExchange 清算经验）

链路 核心挑战 迁移 CoinExchange 的标准答案
资产余额（Token Balance） 多链区块扫描回滚、RPC 节点分叉数据、余额并发更新 ✅ ​同 MemberWalletDao 设计​：UPDATE wallet_token SET balance = balance + ? WHERE account_id=? AND token=? AND balance >= ?（条件原子 UPDATE = DB 行锁 CAS），杜绝先查后改 TOCTOU 漏洞；再结合 ​每小时全量对账任务​（链上真实余额 vs 本地 DB 汇总 = 差异告警）
交易历史落库 链上回滚 reorg、RPC 返回重复 tx、重复扫描入库 ✅ ​同成交明细幂等设计​：主键用 (chain_id, tx_hash, log_index) 唯一索引（EVM 的 event log）；Solana 用 (chain_id, signature, instruction_index)；INSERT 用 ON DUPLICATE KEY UPDATE status=?；reorg 处理 = UPDATE confirmed=false WHERE block_height > (最新确认高度-20) 重新回扫
上链广播状态追踪 交易 stuck、Nonce 冲突、用户重复提交同笔交易 ✅ ​同 Kafka 重试队列设计​：广播任务进 Redis ZSET 持久化重试队列（score=下次重试时间戳）；指数退避 delay = 1s * 1.5^retry_count，超阈值进 DLQ 告警人工介入；状态机 PENDING → BROADCAST → MEMPOOL → CONFIRMED / FAILED / DROPPED
代币列表与价格聚合 跨链 token 重名、假币诈骗、价格喂价延迟 ✅ ​同 CoinProcessor 聚合模式​：每个链一个 ChainProcessor，增量聚合代币列表 + 链上 metadata（name/decimals/logo），白名单/黑名单机制；价格聚合用 OKX/Binance oracle 三取二中位数防单点喂价错

✅ 非它不可的 Nonce 管理（高频面试题 + 伪代码）

​Nonce 三大坑​：① 同一用户并发两笔 Nonce 重复 ② 交易失败了 Nonce 没释放后面全卡住 ③ 节点返回的 latest/pending Nonce 不一致

​**标准答案伪代码（迁移分布式锁思想）**​：

Go

// 取可用 Nonce
func getNextNonce(ctx context.Context, accountId string, chainId int) (uint64, error) {
    // 1. 先拿 DB 已记录的"最大已确认 Nonce"（避免节点乱序）
    dbNonce := repo.GetMaxConfirmedNonce(accountId, chainId)

    // 2. 再查节点 pending Nonce（含 mempool 中还没打包的）
    nodePendingNonce, _ := rpc.GetTransactionCount(ctx, address, "pending")

    next := max(dbNonce + 1, nodePendingNonce)

    // 3. ✅ 关键：用 Redis SETNX 抢占分布式 Nonce 锁，10 分钟自动过期
    //    （同我们 CoinExchange 的 Kafka 分区串行思想，把并发 Nonce 请求串行化）
    locked, _ := redis.SetNX(ctx, fmt.Sprintf("nonce:%d:%s:%d", chainId, accountId, next), txId, 10*time.Minute).Result()
    if !locked {
        // 这个 Nonce 被别人抢到了，递归+1 找下一个空位
        return getNextNonce(ctx, accountId, chainId, next + 1)
    }
    return next, nil
}

// 交易终态（成功/失败）释放 Nonce 锁
func releaseNonce(chainId int, accountId string, nonce uint64) {
    redis.Del(ctx, fmt.Sprintf("nonce:%d:%s:%d", chainId, accountId, nonce))
}

✅ EVM vs Solana 交易模型核心差异（一面二面必问）

维度 EVM Solana
账户模型 Account-based（余额存账户） Account-based + ​**Program Derived Address (PDA)**​（合约托管资产，PDA=程序派生地址无私钥）
顺序 Nonce 单账户严格递增 Nonce 用 recentBlockhash（2 分钟窗口过期）代替 Nonce；需要顺序用 Durable Nonce 账户
并发能力 同一账户并发受 Nonce 限制（串行） ​**交易显式列出所有访问账户（Read/Write）**​，VM 自动并行不冲突的交易（>10 万 TPS）
Gas 模型 GasLimit × GasPrice（EIP-1559 baseFee+priorityFee） ComputeBudget: 固定 max compute units × compute unit price per CU
签名 secp256k1 + ECDSA（v/r/s） ed25519 + 可多签（多 signer 数组）
回滚机制 单笔交易 revert，消耗 gas，已执行 state changes 全回滚 Instruction 级 returnData；整个 tx 失败回滚；跨程序调用 CPI 嵌套可嵌套 revert
代币标准 ERC-20（approve/transferFrom 两步） SPL Token（​ATA 关联代币账户​，1 地址 1 mint 唯一 ATA）

四、Golang 技术基础 & 分布式系统（迁移 CoinExchange 经验）

✅ Golang 高频面试要点 + 结合项目经验答法

题目 迁移 CoinExchange 的标准答案
Goroutine 调度模型 GMP 答：G=用户协程（类似我们 Kafka 每条 HandleTradeThread 任务），M=内核线程，P=逻辑处理器持有本地 G 队列；调度时机：函数调用栈检查、channel 阻塞、GC STW；项目里用 ThreadPoolExecutor(30, 100, 1024) 限制并发上限 = Go 里用 buffered channel + worker pool 控制 goroutine 数，避免无限制 goroutine 泄漏。
Channel 无缓冲 vs 有缓冲 无缓冲 = 同步交接；有缓冲 = 本地任务队列（对应我们 1024 LinkedBlockingQueue）；关闭时机生产者侧，读取用 for v := range ch；​竞态排查​：Go 用 -race 编译选项 ≈ Java 里 synchronized 缺漏的内存可见性问题排查。
Context 作用 跨 API 边界传递取消信号 + 超时 + 元数据（traceId）；项目里 Kafka 超时、DB 查 for update 长事务都需要 ctx 超时中断，对应 Java 里的 Thread.currentThread().interrupt()。
标准库 json vs sonic/ffjson 高频行情推送序列化用 github.com/bytedance/sonic JIT 编解码，速度是 encoding/json 3x；对应我们 CoinExchange 用 Fastjson 的原理一致，高频场景​序列化/反序列化本身就是瓶颈​。
Gin / Go-zero / Gorm 选型对比 Gin：轻量 HTTP 框架（5 万 qps 单实例）；Go-zero：微服务全家桶（内置 goctl 代码生成、熔断、JWT、prometheus）；Gorm 坑——​Preload 多对多 1+N 查询​，用 Joins 或原生 SQL 解决（对应我们 JPA 的 findOne N+1 坑）。

✅ 分布式系统必问 + 迁移 CoinExchange 答法（​这是你最大亮点，一定要结合项目说​！）

题目 迁移式标准答案（开头就提「我在之前做交易所撮合/清算项目时实际落地过类似方案」）
幂等设计怎么做？ 我做过交易所清算模块，三层幂等：① 消息级唯一键 Kafka 业务ID + DB 唯一索引；② 状态机 UPDATE WHERE（UPDATE order SET status='COMPLETED' WHERE status='TRADING'，返回 0 行表示已处理）；③ 布隆过滤器防历史海量重复；钱包转账场景直接迁移：唯一键 (chain_id, from_address, nonce, to_address, value) 做幂等。
分布式锁选型？ 三种都用过：① DB 行锁（SELECT ... FOR UPDATE），清算钱包余额变更用这个最稳；② Redis SETNX + 自动过期 + Lua 原子续约，Nonce 抢占这个用；③ ZooKeeper/Etcd 临时节点（需要公平锁/可监听释放时用）。实际项目 95% 的场景 Redis 锁足够。
消息队列怎么保证不丢？ 我做过交易所撮合 Kafka：① 生产者 acks=all + retries=MAX + idempotence=true + transactional；② Topic min.insync.replicas=2；③ 消费端 enable.auto.commit=false + 手动 Ack；④ 失败消息进 Redis ZSET 持久化重试队列（指数退避），超次数进死信队列告警；钱包广播任务完全一样的链路。
熔断限流？ 用 Go-zero 内置的 Sentinel/go-breaker：半开/半闭/全开状态；限流：令牌桶（瞬时 QPS 控制） + 漏桶（平滑请求速率）；项目里 API 下单接口 1000 qps/用户，超出返回 429；钱包节点 RPC 层做熔断避免 Infura 单点故障切 Alchemy。
亿级数据存储优化实战？ 三招：① ​垂直分表​（钱包账户表 / 余额表 / 交易历史表 分开）；② ​水平分库分表​（ShardingSphere 按 account_id 哈希分 32 库 × 32 表，单表控制在 2000w 内）；③ ​冷热分离​（交易历史 3 个月一个分表，90 天前归档 ClickHouse）；索引优化：联合索引用区分度最高的列放前面 + 覆盖索引避免回表。

✅ MPC / TSS 钱包原理（一句话 + 优缺点）

MPC (Secure Multi-Party Computation) TSS (Threshold Signature Scheme)
本质 签名过程​多方协同计算​，私钥分片永远不完整存在任何一方 私钥 DKG 分布式生成 → (t,n) 阈值签名，任意 t 片可出合法签名
常用算法 Yao's Garbled Circuits / GMW / SPDZ GG18/GG20 (ECDSA)/ Lindell (EdDSA)
优点 不要求椭圆曲线支持，通用性强 ECDSA 签名输出与普通单签完全一致（链上不可区分），链上不用改
缺点 通信轮次多（8~20 轮）延迟高 ECDSA TSS 数学复杂，特定曲线才能实现（Ed25519/Schnorr 简单）
项目实战 Coinbase Custody / Fireblocks Binance MPC 钱包 / ZenGo / 比特儿 MPC

✅ AA 智能合约钱包（EIP-4337 / EIP-7702）高频题

EIP-4337 核心链路（核心 = 把签名验证从 EOA 搬到链上合约里）：

 用户签 UserOperation (UO)
    │    {sender, nonce, initCode(首次部署), callData, ... , signature}
    ▼
 ① 放入 Alt Mempool（替代标准 mempool 的替代内存池）
    │
    ▼
 ② Bundler（打包节点）收集一批 UO → 调用 EntryPoint.handleOps()
    │   EntryPoint: 链上统一入口合约
    │
    ▼
 ③ EntryPoint 调用 sender.validatePaymasterAndData → validateUserOp → Paymaster 代付 Gas
    │   (Gas 抽象：用户不用持有 ETH 付手续费，用 USDC / 项目方补贴均可)
    │
    ▼
 ④ EntryPoint 调用 sender.call(callData) 执行用户业务逻辑
    │
    ▼
 ⑤ 失败 → EntryPoint 调用 validatePaymasterUserOp 补偿 Gas 给 Bundler（避免 DoS）

关键周边：
 • EIP-7702 (Set EOA Account Code) = 临时把普通 EOA 设置成 AA 验证逻辑，不用真部署合约
 • Safe (Gnosis Safe) = 多签钱包鼻祖，主流机构/项目方选择（支持模块 + 回退机制）
 • Biconomy / Alchemy Account Kit = 第三方 AA SDK，帮你集成 Paymaster/Bundler

✅ 亿级数据双写/迁移/版本兼容（加分项实战方案）

就用你熟悉的对账 + 双写校验思路答：

【方案：四阶段蓝绿双写 + 增量校验 + 灰度切换】
T0~T2w  准备期：新表结构建好 + 部署 CDC（Canal/Debezium）监听旧表 binlog
T1~T4w  阶段①（只读+双写校验）：
         a) 所有写入同时写旧表 + 新表（失败回滚）
         b) 每 10 分钟「对账任务」：SELECT 旧表 MINUS 新表（按主键对比每列 hash）
            → 差异入 discrepancy_log 表告警，查出双写 BUG 修
T3~T6w  阶段②（灰度读新表）：
         a) 按 user_id % 100 = 1 → 灰度 1% 流量读新表
         b) 同时**影子读**旧表，两边结果逐字段对比不一致告警
         c) 灰度比例 1% → 10% → 50% → 100% 逐步放大
T7      阶段③（切主）：
         a) 100% 读写新表
         b) 旧表做 1 周 CDC 反向同步（新表变更回写旧表）保持可回滚
T8~     阶段④（收尾）：
         a) 观察 2 周无问题 → 停 CDC + 归档旧表冷备
         b) 回滚预案：反向双写保留 2 周，一键切回读旧表
​

💡 迁移经验：这就是我们 CoinExchange 「MatchLog 拉回重放 + 三方对账」的升级版，任何数据迁移离不开「双写 + 对账 + 灰度 + 回滚」四件套，缺任何一环都是生产事故导火索。
